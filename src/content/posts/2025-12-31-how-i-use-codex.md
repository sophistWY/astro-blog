最近这段时间，我越来越多地把 Codex 当成一个可以一起完成事情的协作伙伴，而不只是一个“帮我写几行代码”的工具。

我给它的任务，往往不是一个已经拆好的函数，而是一句更接近真实工作的描述：帮我找到正确的博客项目、把站点迁移到 Astro、仔细检查旧文章里的图片和 PDF、把首页做得更有质感，或者把后台接好，让以后发文章方便一点。

回头看，真正改变我的并不是某一个生成结果，而是工作方式变了：我开始把目标、上下文和验收标准一起交给它，再根据实际结果不断纠正方向。这篇文章只总结目前有真实协作记录的这段时间，不把没有证据的经历补写成事实。

## 第一个经验：先确认“到底是哪一个项目”

最开始，我只是想让 Codex 帮我找 GitHub 上的个人博客项目。这个任务看起来很简单，但很快就发现，找到一个“看起来像”的仓库，和找到真正正在使用的仓库，是两回事。

后来我明确了博客地址、仓库和部署关系，才把工作范围固定下来。这个过程让我意识到，使用 AI 时，第一步不是马上让它开始改代码，而是先确认对象：项目在哪里、线上地址是什么、当前版本是什么、哪些内容不能动。

如果对象都没有对齐，后面做得越快，偏差就越大。

## 第二个经验：迁移项目时，内容比框架更重要

博客迁移到 Astro 后，最初的重点当然是页面能不能构建、部署能不能成功。但真正让我反复检查的，是旧文章有没有被准确搬过来。

旧文章里有不少本地图片、历史路径和 PDF 附件。只把 Markdown 文件复制过去，并不代表迁移完成；图片可能加载失败，PDF 可能被漏掉，少数文章的路径也可能已经不适合新站点。

所以这次迁移的工作顺序慢慢变成了：

1. 扫描文章和资源。
2. 修复异常的本地图片路径。
3. 确认 PDF 能打开、能下载。
4. 恢复原来的分类和标签。
5. 逐个检查旧文章 URL。
6. 最后再处理首页和视觉细节。

这也是我对 AI 协作最重要的一次提醒：漂亮的页面不能证明内容迁移是正确的。对于自己的历史文章，必须把“准确”放在“好看”之前。

## 第三个经验：要敢于指出“这不是我的内容”

在整理博客时，我发现有些文章的标题和内容看起来不像原来的写法，甚至有臆造的感觉。这个问题不能用“整体差不多”来掩盖，因为博客文章是个人积累，不是可以随便补写的演示数据。

我后来会明确要求：重新扫描原文，按原内容搬运；带 PDF 的文章要以附件和正文为准；不确定的地方不要自行补全。这样的纠正非常重要，也让我更清楚地认识到，AI 生成得越流畅，越需要检查它有没有悄悄改变事实。

Codex 很适合做整理、搜索、批量修改和验证，但它不是记忆库。没有证据的地方，就应该标记为不确定，而不是用一段顺滑的文字填上去。

## 第四个经验：视觉工作需要“看结果”，不能只看代码

首页改版过程中，我几次觉得“代码应该没问题”，但真正打开页面后，还是会发现层次、留白和比例不对。后来我会直接让 Codex 本地运行站点，再通过浏览器看实际效果，然后继续调整。

这和单纯检查 CSS 文件很不一样。页面是否高级，不是由某一条 CSS 属性决定的，而是由整体节奏、字体、颜色、间距和内容密度共同决定的。浏览器标签页的 favicon 也是一样，文件存在不代表浏览器已经显示了正确的图标，还要考虑缓存和真实页面效果。

所以现在遇到界面任务，我更习惯用这样的循环：

> 修改 → 本地运行 → 浏览器查看 → 指出具体问题 → 再修改。

代码检查和视觉检查是两种不同的验收，缺一不可。

## 第五个经验：把发布流程做得足够无聊

博客迁移完成后，我不希望每次发文章都要打开编辑器、手动处理资源、执行命令，再等待部署。于是又接入了 Sveltia CMS，让文章可以在浏览器后台编辑，图片和 PDF 也能一起上传，提交后由 GitHub Actions 自动构建并发布。

现在发布一篇文章的流程变成了：写内容、上传附件、保存、等待部署。代码仓库仍然是唯一的内容来源，但日常写作不必再关心构建细节。

我越来越认同一个简单的判断：如果发布流程很有技术感，说明它可能还不够好。真正好用的工具链，应该让人把注意力放在内容上，而不是放在“这次命令有没有敲对”。

## 我现在会怎样给 Codex 下任务

相比“帮我优化一下”，我更愿意把任务说成一个可以验收的目标：

- 先说明项目和线上地址，避免找错对象。
- 说明哪些内容必须保持原样，尤其是文章、图片和 PDF。
- 把审美要求说成具体感受，例如更克制、更有层次、减少模板感。
- 要求本地运行或线上检查，而不是只接受代码已修改的结论。
- 涉及发布时，明确发布范围、文章日期和是否直接上线。

这样做并不会让 AI 变得“更聪明”，但会让协作结果更接近真正想要的东西。

## 最后

这段时间使用 Codex 后，我最大的收获不是少写了多少代码，而是开始把很多模糊的事情变成可执行、可验证的流程：找到真实项目，保留真实内容，看到真实页面，完成真实部署。

AI 最有价值的地方，可能不是替我做决定，而是把我已经想做、但一直拖着没做的事情推进下去。前提是，我要持续提供上下文，也要保留最后的判断。
